# 常驻看护进程 · 设计(2026-09-12)

> 这份 spec 取代 2026-09-10 那份设计里的 §5.2(重启实现)与 §3(启动方式)两处。
> 其余部分(注册表条目形态、config.json 契约、启用/停用语义)仍以旧 spec 为准。

## 1. 为什么改

两个已归档的实测缺陷**同源**:

| 缺陷 | 现象 | 根因 |
|---|---|---|
| **F8** | 一键重启后 DSH 再没起来,页面永远"重新连接中" | 新实例由 WMI 助手启动,失败/被跳过时无人接管 |
| **F9** | 每条命令弹一个 Windows Terminal 窗口并残留 | `spawnDsh` 用 `detached: true`(= DETACHED_PROCESS)让宿主**没有控制台**;而沙箱不允许给子进程单独隐藏控制台(受限令牌下 `0xC0000142`),子进程必须共享宿主控制台 → 每个 runner 只能新建一个 → Windows 11 交给 Windows Terminal |

共同的根:**宿主没有可共享的控制台**,而"谁启动 DSH"这件事没有主人。

## 2. 目标 / 非目标

**目标**

1. 消除"每条命令一个可见控制台窗口"。
2. 消除"重启失败后 DSH 下线且无人接管"。
3. 删掉 WMI 参与重启的那套复杂度(它正是"重启变关机"事故的来源)。

**非目标(YAGNI)**

- ❌ **不做全时看门狗**:DSH 被用户主动关掉/崩溃时**不去复活它**。一个关不掉的进程比一个偶尔起不来的服务更糟。
- ❌ 不做"看护看护者"的第二层进程。
- ❌ 不改注册表条目的形态:仍是 `HKCU\...\Run` 一条,仍指向 `bootstrap.vbs`。
- ❌ 不改 `config.json` 的结构。

## 3. 三个已定决策

| # | 决策 |
|---|---|
| **1** | 看护进程职责:**持有隐藏控制台 + 执行"重启请求" + 该起来却没起来时有界重试**。不做全时看门狗 |
| **2** | **停用自启 = 只取消开机自启**:看护进程与 DSH 继续跑,看护进程在下次重启后自然消失(条目已删)。**卸载 = 显式停止看护进程**(DSH 随之结束) |
| **3** | 点重启时若看护进程没在跑:**先按登录入口把它拉起来并确认它活着,再让它接管**;拉不起来则**当场拒绝重启、DSH 保持不动** |

## 4. 架构

```
HKCU Run  →  wscript bootstrap.vbs  →  node service.js supervise --config <config.json>
                                          │  （wscript 的 Run(cmd, 0, False) 让它拿到一个隐藏控制台）
                                          ├─ 端口探测(重试窗口) → spawn DSH（attached）→ waitForPort → runHook
                                          └─ child.on('exit')  ← 不轮询,持有子进程句柄
```

- **`spawnDsh` 改为 `detached: false, windowsHide: false`** → 宿主 attached 在看护进程的隐藏控制台上 → 沙箱子进程共享它 → **零弹窗**。
- 看护进程是**唯一**启动 DSH 的东西。
- 判断宿主死活用 `child.on('exit')`,**不轮询端口**。

## 5. 生命周期与状态机

看护进程有**两种启动形态**,区别只在"启动时端口被谁占着":

```
形态 A · supervise --config <cfg>                    （登录入口 / 手动恢复）
  [ 探测端口 ] ──空闲──► spawn DSH(attached) ──► waitForPort ──► runHook ──► [ 看护中 ]
       │                                   │            │                      │
     被占                              spawn 失败      超时                     │
       │                                   └─────┬──────┘                      │
       ▼                                         ▼                             │
  [ 记日志 → 退出 ]                    [ 原地重试 ]                            │
  （别人已经在服务 DSH,                                            成功 ──────┘
    没什么可看护的)                  间隔 1s 起、每次 ×1.5、
                                     总计上限 5 分钟 ──耗尽──► [ 记日志 → 退出 ]

形态 B · supervise --config <cfg> --takeover <pid>   （决策 3 的按需接管）
  [ 探测端口 ] ──被占──► [ 等 <pid> 退出（有界，默认 30s）] ──► [ 按形态 A 的空闲分支走 ]
       │                              │
     空闲                        等不到 → [ 记日志 → 退出 ]（DSH 不动，路由那头会拒绝这次重启）
       └──────────────────────────► spawn DSH
```

**为什么必须有形态 B**:按需接管时当前 DSH **还占着端口**。如果这时只按形态 A 走,看护进程会"跳过",而它**没有子进程** —— 路由退出 DSH 后它收不到任何 `exit`,于是没人重起。形态 B 让它明确知道"有一台占着端口的 DSH 即将退出,退出后由我接手"。

**看护中**(两种形态合流之后):

- 依据 `child.on('exit')` 判断,不轮询;
- 有 `restart.request` 且其中 pid 与刚退出的子进程一致 → **清掉标记** → 重新 spawn;
- **其它情况(用户主动关掉、崩溃)→ 什么都不做**(决策 1:不做全时看门狗);
- 有 `restart.request` 但 **pid 不匹配** → 不 spawn(防陈旧标记误触发);
- 收到 stop 标记 → 退出。

**文件契约**(都在 `~/.dsh/dsh-autostart/`):

| 文件 | 写入者 | 含义 | 消费后 |
|---|---|---|---|
| `restart.request` | 路由(写 pid 后 `process.exit(0)`) | 这次退出是用户要的重启,针对该 pid | 看护进程**删除** |
| `supervise.stop` | CLI(写**目标看护进程的 pid**) | 请退出 | 看护进程**删除后退出** |
| `supervise.pid` | 看护进程自称 | 单实例守卫 | 退出时尽力删除 |

三者都是**尽力而为**(删不掉不影响正确性)。陈旧文件由**pid 比对**消解:看护进程只处理**指向自己**的 `supervise.stop`,以及 pid 与自己刚退出的子进程一致的 `restart.request` —— 所以一个陈旧的 stop 标记不会让下次登录的看护进程立刻自杀。

## 6. 失败方向(最关键)

**顺序永远是"先确保接管者活着,再放手"**:

1. 点重启 → 确认看护进程在跑(`supervise.pid` + 存活检查);
2. 不在 → 按**形态 B** 把它拉起来(`supervise --config … --takeover <当前 DSH pid>`),它能拿到隐藏控制台,并**确认它真的活了**;
3. 确认之后,才写 `restart.request`、退出当前 DSH。

**任何一步失败 → 当场拒绝重启、DSH 保持不动**,回一个明确错误。**绝不出现"DSH 已下线、没人接管"的窗口** —— 那正是 F8/F5 两次事故的根源。

**必须承认的单点**:看护进程死 = DSH 死(控制台继承的直接后果,见 §3 决策 1 的讨论)。缓解:它本身几乎不做事(等一个 exit 事件、起停一个子进程),没有会抛的循环。不再加第二层看护。

## 7. 迁移与兼容

| 事项 | 处理 |
|---|---|
| 已装用户的 `bootstrap.vbs` | 它是由 `enable` 生成并**快照**的(见 F1),内容写死 `service.js start --config …`。因此 **`start` 保留为 `supervise` 的别名** → 老用户**不需要重新点启用**就获得新行为 |
| 重复启动看护进程 | **单实例守卫**:`supervise.pid` + 存活检查。第二个实例发现已有活的看护进程就立刻退出(幂等),避免两个看护各起一个 DSH 抢端口 |
| 恢复文档里的 `wscript bootstrap.vbs` | `bootstrap.vbs` 用 `Run(cmd, 0, False)` 不等待,所以"看护进程常驻"对用户**无感**,该命令仍是正确的恢复手段 |
| `--second-chance` / `--delay` | **删除**。被"看护进程原地重试"取代(它们是无看护进程时代的产物) |
| `config.json` | 结构不变 |
| 旧 spec 的 §5.2 | 由本 spec 取代;`docs/ACCEPTANCE.md` 的 F5/F8/F9 补一条"由本设计根治" |

## 8. 会删掉什么

- `service.js`: `restart --pid` 分支、`runRestart`、`scheduleSecondChance`、`--second-chance`/`--delay` 解析;
- `launch-helper.js`: 收紧为**只负责把看护进程送出 DSH 的 Job**(仅"按需接管"时使用);
- **WMI 不再参与重启**。

保留:`isPortListening` / `waitForPort` / **端口探测重试窗口**(F8 的修复,与本设计正交且仍然必要)、hook 机制、"不许抢端口"的安全底线、**`waitForProcessExit`**(形态 B 要等被接管的 pid 退出)。

## 9. 测试

**单元**(每个状态转移一条):

1. 形态 A:端口被占 → 记日志 → 退出(不 spawn、不留守);
2. 形态 A:启动成功 → spawn 一次 → 等端口 → 跑 hook;
3. 形态 A:`waitForPort` 失败 → 原地重试(间隔 ×1.5),直到上限;
4. 形态 A:重试耗尽 → 记日志 → 退出码 0(不留僵尸);
5. 形态 B:端口被占 → **等 `--takeover <pid>` 退出** → 然后 spawn(这一条就是自查抓到的那个漏洞);
6. 形态 B:等不到 pid 退出(超时)→ 记日志 → 退出,且**不 spawn**;
7. 形态 B:端口已空闲 → 直接 spawn(不必等);
8. 收到 exit 且**有**匹配 pid 的 `restart.request` → 清标记 → 重新 spawn;
9. 收到 exit 且**无**请求 → 不 spawn(决策 1);
10. `restart.request` 的 pid **不匹配** → 不 spawn(防陈旧标记误触发);
11. `supervise.stop` 指向自己 → 删除标记 → 退出;
12. `supervise.stop` 指向**别的** pid → 忽略(陈旧的 stop 不能让新实例自杀);
13. 单实例守卫:已有活的看护进程 → 立刻退出且不 spawn;
14. 按需接管:**看护进程起不来 → 拒绝重启且 DSH 不动**(路由侧)。

**真机**(缺一不可):

1. 登录路径走一遍,**枚举可见控制台窗口应为空**(F9 的判据,睡 3 秒再枚举,避免时序假象);
2. 点一次重启:页面恢复,**全程无新窗口**;
3. 停用自启后 **DSH 仍在跑**;
4. 按需接管:手动 `npx dsh web` 起一个 DSH → 点重启 → 应由看护进程接管,且此后无弹窗。

## 10. 风险 / 未验证的前提(实现第一步必须先验)

⚠️ **核心前提**:宿主 attached 在**长期存活**的看护进程的隐藏控制台上 → ① 不弹窗;② 稳定存活不被打断。

我们**已测到**的:attached 子进程会在父进程退出后 ~10 秒内被杀;detached 的活过 2.5 分钟。
我们**没有确证**的:① 那个"被杀"的确切机制(控制台销毁还是别的);② **父进程长期存活时,attached 子进程是否长期稳定**;③ 该控制台是否真的对所有沙箱子进程可见(于是真的不弹窗)。

→ **实现第一步是一次真机验证**(起一个带隐藏控制台的常驻进程 + attached 长命子进程;枚举窗口;观察数分钟)。**不通过就停下来重新设计**,不要在未验证的前提上继续写代码。

其它风险:

- **单点**:看护进程死 = DSH 死(已接受,见 §6);
- **隐身进程**:停用自启后看护进程会留到下次重启(决策 2 已接受,需在 README 说明);
- **注册表被动手改**:`isOurEntry` 只认自己的值名,用户手改条目会让看护进程的"自启"身份失效(与旧设计相同)。
